# S-UI-X Extended v1.0.6-beta2

Backfills sudoku/mieru client links at startup and fixes the empty QR code in the AmneziaWG 2.0 device manager.

## Sudoku/mieru link backfill

Sudoku and mieru links (added in v1.0.6-beta1) are generated when a client or an inbound is saved. Clients assigned to a sudoku/mieru inbound before the beta1 build stored no local link, so they had no URI and no QR until an operator re-saved them.

- `ClientService.RegenerateMissingLocalLinks` runs at startup after `InitDB`. For every client on a sudoku/mieru inbound it regenerates the local links through the existing `rebuildClientLinks` path and writes back only when the result changed.
- Non-local links are kept. Missing mieru credentials (per-user name and password) are filled in on the first run and persisted, so the random password does not churn on later starts. Clients that sit on no sudoku/mieru inbound are never touched.
- The pass is wired in as non-fatal: a failure logs and lets the app continue. A second start is a no-op.

Tests cover the sudoku add, idempotency, the mieru credential path, the untouched-client guard, and the no-inbound fast path.

## AmneziaWG 2.0 QR code

The QR button in the AmneziaWG 2.0 device manager (client modal, Devices tab) rendered an empty picture for full AWG 2.0 configs. Three things lined up:

- `RenderAWGConfigQR` rejected any config over a hand-picked 1500-byte cap and returned `ErrAWGConfigTooLargeQR`.
- The `GetClientAWGDeviceQR` handler passed that error to `jsonMsg`, which follows the SPA envelope and always answers HTTP 200 with a JSON body.
- The frontend requested the QR as a blob and fed it straight into an `<img src>` without checking the content type. A JSON body under a 200 status is not an image, so the browser drew nothing.

An AWG 2.0 config carries the junk and init-packet fields (I1-I5, J1-J3, Itime). With those filled in it runs past 1500 bytes, so the cap fired on exactly the configs the feature is meant to serve.

Changes:

- Dropped the 1500-byte constant. `RenderAWGConfigQR` now encodes at Low error-correction (widest byte capacity, about 2953 bytes at QR version 40) and reports `ErrAWGConfigTooLargeQR` only when the codec itself refuses the payload. The real limit comes from the QR format, not a magic number.
- Added J1, J2, J3 and Itime to the rendered client config. They were parsed from the endpoint options but never written, so AWG 2.0 clients received an incomplete obfuscation profile.
- `GetClientAWGDeviceQR` now returns a genuine HTTP status on failure: 422 when the config is too large for a QR, 500 otherwise. The binary endpoint no longer hides an error inside a 200 response.
- The client modal checks the response content type before building the image. On anything that is not an image it reads the server message (or a `qrFailed` fallback) and shows an error, so the operator is pointed at the `.conf` download instead of a blank dialog. The message string is added to English, Russian and both Chinese locales.
- The Telegram bot path (`paidsub`) already handled `ErrAWGConfigTooLargeQR` and inherits the wider capacity through the same renderer.

## Notes

- The QR codec limit at Low error-correction is 2953 bytes. A config with unusually long I-parameters can still exceed it; that case now degrades to the `.conf` download and a clear message rather than a blank image.
- Existing sudoku/mieru clients get their links on the next panel start, no manual re-save needed.
